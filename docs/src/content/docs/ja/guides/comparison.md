v5以降のリリースでは、`WebComponent` ベースクラスはカスタム要素の仕様への準拠をより厳密にし、JSコンポーネントの作成に関する期待値と安定したHTMLの振る舞いを組み合わせることで、QOL（生活の質）の改善と全体的な堅牢性を実現しました。現在では、その場での再レンダリング、HTMLのboolean意味論、オーバーライド可能な属性コンバーターなど、数々の改善が備わっています。

このページでは、これらの利点とそのコストを文脈の中で示します。類似のWeb Componentライブラリと比較してWCBのサイズはどれくらいか、各ライブラリはカスタム要素をゼロから書くのに比べて何をもたらしてくれるか、そしてどんなときにWCBが正しい選択となるかです。

## 実測サイズ: 各ライブラリで同じコンポーネントを実装

以下の数値は、各ライブラリで書いた同一の最小限のカウンターコンポーネント（1つのリアクティブな `count` prop、クリックハンドラー、変更時の再レンダリング）を `esbuild --bundle --minify --format=esm` でバンドルし、gzip（レベル9）とbrotli（品質11）で圧縮して**実測**したものです。これは「最初のコンポーネントの実コスト」、つまりライブラリのランタイム＋コンポーネントコードとしてブラウザがダウンロードするすべてを表しています。

実際に動く様子はこちら: [ライブラリ比較デモ ↗](https://demo.webcomponent.io/examples/library-comparison/) — すべてのカウンターが並んで動作し、各ライブラリのソースと、下表を生成する `measure.mjs` スクリプトを確認できます。

| ライブラリ                  | バージョン | 最小化後 | Gzip    | Brotli     |
| ------------------------- | ------- | -------- | ------- | ---------- |
| **web-component-base**    | 6.2.0   | 6.6 kB   | 2.9 kB  | **2.6 kB** |
| `@elenajs/core`           | 1.0.1   | 9.1 kB   | 3.7 kB  | 3.4 kB     |
| `lit`                     | 3.3.3   | 15.3 kB  | 5.9 kB  | 5.3 kB     |
| `@microsoft/fast-element` | 3.0.1   | 44.8 kB  | 13.6 kB | 12.2 kB    |
| バニラ `HTMLElement`      | -       | 0.6 kB   | 0.3 kB  | 0.2 kB     |

規模感として: v5.2〜v6.2のすべての作業を経てなお、WCBのカウンターはElenaより**約23%小さく**、Litより**約52%小さく**、FASTより**約79%小さく**なっています。

:::note[11ty WebCがここにない理由]
WebCはコンパイル時ツールです。Eleventyのビルド中にコンポーネントを解決し、クライアントランタイムなしのプレーンなHTMLを出力します。上表の各行はすべて、ライブラリが*ブラウザ上でランタイムに*何を行うかについてのものなので、並べて比較すると異なる2つのものを測ることになってしまいます。もしあなたのコンポーネントがビルド時に静的であるなら、WebCは別の問題を解決してくれます。
:::

## SSR／ハイドレーション対応の比較

SSR列の4つのうち3つは、そのパッケージ自身が公表している**安定性の位置づけ**をそのまま引用しています。`@lit-labs/ssr` はこの中で最も成熟しています。2021年以来Lit Labsのプレリリース表記（「破壊的変更が入る、あるいはサポートが終了する可能性がある」）を掲げ続けてはいるものの、メジャーバージョンは4に達し、活発にリリースされ、メンテナンスされたEleventy統合を支えています。`@elenajs/ssr` はアルファ版であり、そう明記されています。FASTも自身のSSRを実験的と位置づけています。

WCBにはSSRパッケージ自体が存在しないため、その ⚠️ は他の3つとは意味が異なります。状態の側はすでに機能します。宣言されたすべてのpropが、サーバーが書き出した属性から、宣言された型を通して初期化されます。HTMLを出力できるサーバーであれば何でも構いません。一方、DOMの側は機能しません。最初のクライアントレンダリングがサーバーのマークアップを引き継がずに置き換えてしまうため、サーバーHTMLは初期表示専用にとどまります。`@elenajs/core` もここではWCBと同じ振る舞いをします。動的なコンポーネントの最初のクライアントレンダリングは、サーバーのマークアップを引き継がずに置き換えます。
